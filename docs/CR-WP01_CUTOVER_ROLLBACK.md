## 1. 边界与现有事实

现有migrate.py校验已应用SQL的SHA-256，不能改写001～009。旧auth.grant_consent可新建purpose授权，results保留purpose读取，旧二进制不认识新schema/version/epoch；只加标志或撤销当前consent不能阻断旧服务继续授权。compose当前API/Worker共用PG连接配置，新运行角色隔离是未来变更，不在本轮修改。

【已批准】正式切换统一终止旧目的授权，不自动转码；不创建新的内容备份或含内容整库/系统快照；旧副本先核实、隔离、获准处置；切换不得删除源任务或复活授权。WP02编写/隔离测试，WP07另批执行，S3-12历史清理再另批。

迁移需事务/版本锁、可重放、错误整体回滚；跨文件不是整批原子，任何中间版本都应维护状态、不开放旧服务。M1/M2可在隔离库验证，不代表业务库已迁移。M3授权终止/epoch切换及M4数据/能力清退不是放入普通app.migrate扫描目录就自动执行的资产。010起普通迁移只扩展结构；M3由WP07独立受控维护入口、精确expected_deployment_id/protocol/revision、显式执行授权启动，终止旧授权/epoch更新/切换事件同事务，失败保持维护。M4按能力/数据类别另审，历史清理仍需专项批准。新增CHECK/唯一索引前核对旧异常数据；旧多purpose记录不搬成新ACTIVE。

建议协议状态最小记录：protocol_version/min_runtime、auth_epoch UUID、cutover_at、legacy_disabled_at。独立删除控制卷另存无内容security_epoch与部署身份；DB/卷不匹配时v2启动/就绪拒绝。epoch只向前更新，恢复不能从旧DB覆盖当前外部控制。epoch文件不是授权或内容备份。

## 3. 运行角色与旧二进制阻断（待审批）

- 新runtime角色为非superuser、非owner，不具DDL/角色管理/旧task_consents写权；只给新业务所需表/列/函数权限。迁移和部署维护角色独立，不注入应用容器。
- 正式切换停止旧API/Worker，关闭旧连接、撤销旧运行角色登录/权限、轮换凭证；旧凭证不得继续读写任意用户内容。不能只靠REVOKE表写权，因为旧binary可能仍拥有owner/superuser权限。
- 当前PG_USER可能兼任数据库初始化/维护角色。先建立并验证独立安全维护通道再禁用旧登录，不能锁死唯一部署者；旧管理员维护身份不进入运行服务。
- 旧运行角色若保留为离线owner，至少NOLOGIN且秘密不用于应用，现有连接必须terminate并核对为0；成员关系、SECURITY DEFINER/PUBLIC授权和连接池一并查验。
- 分层就绪：core所有者API必须通过DB协议/删除控制身份/重放；不因缺旧解密key整个API启动失败。生成额外要求当前可写key和有效epoch；管理员resolve/list/content只要求所涉请求解密key及有效epoch，写key不可用/写额度耗尽不影响已有请求（其解密key可用时）；缺某旧解密key仅对应请求fail closed，不全局剥夺其他请求权限；旧解密key缺失仍允许已验证owner取无code Meta和撤销，写key不可用禁止新生成，epoch/DB信任失效不得降级。部署者配置新有效key后再生成，不能因此开放其他内容。新runtime启动校验协议v2/部署身份、删除意图重放并报告support依赖健康；旧路由固定410，无purpose回退。新代码连接错误角色或DB缺结构则503拒绝，不静默降级。
- 保证依赖“实际旧角色断联+最小权限”，不声称新version表能约束不会检查它的S3-10旧binary。

以上含角色权限和维护通道的具体配置须在WP02设计/测试以及WP07操作计划审核，不在本轮创建密码或读取真实.env。

## 4. 正式切换顺序与每步失败状态

| 步骤 | 事前/动作规范 | 失败或中断时 |
| --- | --- | --- |
| D1 固定候选 | WP06证据、代码/文档/迁移SHA、协议、镜像版本、预演结果和授权范围固定 | 证据不全不进入维护。 |
| D2 内容/权限预核 | 部署者核对用户/任务/结果/资产/有效旧授权的计数和归属摘要、配额总账、未完成清理及历史BACKUP未知状态；报告只无内容字段，不复制媒体/摘要 | 未确认归属或受控位置则停止相关切换；不自动做整库dump。 |
| D3 维护隔离 | 停浏览器写入口和旧API/Worker/维护线程，等待/终止并回收旧媒体后代与清理I/O，禁止恢复/复用key | 无停止证明不启动新清理，不把新flock拿到当旧生产者排空证据。 |
| D4 结构/运行身份 | 使用独立维护角色执行已审M1/M2；关闭旧角色连接/登录，配置新最小runtime，固定新真实AES密钥和独立epoch | 故障维持维护；保留独立删除意图，禁止启动旧binary“临时恢复”。 |
| D5 授权切换事务 | M3终止全部未撤销旧目的授权；新表若有演练残留有效授权也终止/清密文；记录切换时间/epoch/事件；不创建新码 | 事务失败不开放；已写外部epoch/意图与DB不一致则守门拒绝，按维护方案补齐。 |
| D6 新服务隔离启动 | 仅协议v2镜像，启动重放；确认nonce/key/epoch、无旧连接、路由410、所有者隔离、后台活性 | 任何检查失败停在维护，不对外签发权限。 |
| D7 授权后开放 | 无内容计数/归属/配额对账一致；在专项授权的新合成任务验证新码/列表/撤销/删除及旧API拒绝；交付“需重新授权”说明 | 失败关入口，保留诊断和控制，不复活旧purpose；真实源任务不为授权试验删除。 |

源数据核验结果只用于当前维护对账，无视频/摘要正文、有效码、Cookie或密钥；这是核验而非备份。生产SQL/存储具体操作到WP07才提交命令和精确目标，批准后执行。

## 5. 回退和灾后恢复

### 5.1 回退原则

首选停服务后的向前修复；只允许已验证协议v2兼容的前一镜像+当前结构回退，不执行删除新结构/恢复旧授权的down migration。首次v2没有可用旧v2镜像时保持维护修复，不回到S3-10 purpose服务。

切换前出错也不以“尚未终止旧授权”为理由擅自开放旧路径；是否中止新发布、继续保持旧服务需要在维护开始前由负责人明确授权，正式切换后绝不恢复无限期授权。凭证/epoch轮换不可被应用回退撤销。源内容不能通过新快照备份来实现回退保障，需披露真实数据损失风险。

### 5.2 任何另行获准的历史快照恢复

1. 网络/服务保持隔离，停止所有生产/清理I/O及旧二进制；核对快照时间、部署身份和当前独立删除控制完整性，沿用90天窗口/证据不足拒绝，不用当前时间冒充快照时间。
2. 保留当前独立删除意图和安全epoch，按M1～M3升级恢复数据；重放全部适用删除，不相信快照内DELETED/COMPLETED就是当前证据。
3. 无条件撤销快照会话及旧purpose/新support请求，清可展示密文、终止幂等重放关联；创建全新auth_epoch和全新AES密钥（仅改key_id不够），旧key永不再加密。
4. 重新禁用/轮换快照可能恢复的旧DB运行角色，结束全部旧连接；只允许新协议runtime。恢复nonce计数/登记也不能使用旧真实key继续加密。
5. 再验证内容删除/对象版本和授权状态；未完成保持隔离或拒绝相关任务，原用户必须重新登录/授权，满足检查才开放。

不支持不经过上述隔离/门禁而直接启动整机旧快照的保证：若旧代码、凭证、网络、独立控制一起回滚，应用无法凭旧状态证明当前撤销；必须外部部署流程先阻止开放。S3-12验证该边界，不擅自删除这些副本。

## 6. 历史副本尚未核验

保持UNKNOWN/UNVERIFIED、隔离恢复，不以BACKUP_INVENTORY_CONFIRMED=true或清空登记来消除提示。已登记、应用可控的BACKUP仍属于待清理受控内容；没有专项批准不能执行其删除，也不能报整体清理成功。在线资产完成可独立记录，overall需所有适用受控资产验证完成；未知基础设施副本另行披露。

维护无内容清单：位置类别/受控标识、归属核实状态、快照时点、隔离/批准/执行/验证状态。必要受控清理及防复活直到处置完成保留；原30天清除期限未达要报告，不擅自延期/删除。S3-11可在新权限基线已验收、历史恢复隔离且无内容备份新增的前提下另行申请，不能借其测试处置历史数据。
