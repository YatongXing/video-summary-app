# Git 分支策略

当前采用。文档整合开始时，本地 implementation 已有未提交的代码、配置及文档变更。远端状态以另行核查为准。

| 分支 | 用途 | 创建基点 | 合并目标 |
| --- | --- | --- | --- |
| `main` | 审阅后的稳定需求基线与后续已批准变更 | 初始提交 | — |
| `architecture` | 架构、安全、数据流设计文档 | `main` 的需求基线提交 | `main` |
| `implementation` | 经批准架构后的产品实现 | 已合并架构的 `main` | `main` |
| `testing` | 经批准实现后的测试资产、自动化和验证记录 | 实现基线 | `main` |

每个分支只承载所属阶段的变更，合并前审阅需求/验收标准对齐。Step 3 的计划及后续实现先保留在本地 `implementation`；提交和推送遵守用户逐次授权，不覆盖远端历史。

## 基线保存与审阅

工作区中的未提交修改与未跟踪文件不会随 HEAD、分支或标签保存。获准保存前，分别审阅已跟踪和未跟踪差异，排除真实配置、凭据、媒体和运行数据，按批准的版本区分 CR-002、WP07-A 与文档变更。旧 S3-10 工作区保存建议保留在 [CR-001 实施计划](archive/cr/CR-001_IMPLEMENTATION_PLAN.md)。

暂存、提交和推送遵守逐次授权。此次文档整合只读检查 Git 差异，保留既有变更。
